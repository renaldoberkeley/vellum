# Vellum - Product Vision

> Internal codename for MarkdownGPT.

## Vision

MarkdownGPT is an AI-native workspace for creating, organizing, and
maintaining collections of related documents.

Traditional document tools treat documents as independent files.
AI chat tools can help write individual documents, but they often lack
an understanding of how documents within a project relate to one another.

MarkdownGPT treats the entire project as context.

A user should be able to explain a new idea, decision, or change once,
and MarkdownGPT should understand which documents are affected, propose
coordinated updates, identify contradictions, and help keep the project's
documentation consistent over time.

The long-term goal is simple:

**Tell MarkdownGPT what changed. MarkdownGPT figures out what documentation
needs to change with it.**

---

## The Problem

Projects rarely consist of a single document.

A software product might contain:

- Product vision
- Product requirements
- Technical architecture
- Engineering principles
- Roadmap
- Research notes
- Decision records

A business might contain:

- Business plan
- Market research
- Product strategy
- Financial assumptions
- Operating procedures
- Marketing plans

A researcher might maintain:

- Research notes
- Literature reviews
- Experiment plans
- Findings
- Draft papers

These documents are related.

However, today's tools largely require users to maintain those relationships
themselves.

When an important decision changes, users must remember:

1. Which documents contain information related to the decision.
2. Which sections need to change.
3. Whether those changes create contradictions elsewhere.
4. Whether terminology remains consistent.
5. Whether older assumptions should be removed or preserved.

AI can help rewrite individual documents, but the user still acts as the
coordination layer between them.

MarkdownGPT aims to remove that burden.

---

## A Motivating Example

Consider a project containing:

```text
vision.md
product-requirements.md
technical-architecture.md
roadmap.md
```

Suppose the team makes an important architectural decision.

Today, someone must manually determine where that decision affects the
documentation and update each file independently.

With MarkdownGPT, the user should be able to say:

> We decided not to depend on third-party pricing APIs. Instead, pricing
> will come from community observations and our own estimation system.

MarkdownGPT should be able to determine:

```text
3 documents are affected.

vision.md
  Update the long-term data strategy.

product-requirements.md
  Add requirements for community price observations.

technical-architecture.md
  Replace the direct pricing API architecture.

roadmap.md
  No change required.
```

The user can then review the proposed changes before accepting them.

The important interaction is not:

**"Edit this document."**

It is:

**"This changed in my project."**

---

## Core Product Idea

MarkdownGPT organizes information around **Projects**.

A Project contains a collection of related documents and the context needed
to understand the relationships between them.

```text
Project
│
├── Documents
│   ├── Document A
│   ├── Document B
│   └── Document C
│
├── Conversations
│
├── Decisions
│
└── Project Context
```

The AI operates at the project level rather than treating every document as
an isolated conversation.

---

## Core Experience

The primary MarkdownGPT workflow should be:

```text
Create or open a project
        ↓
Create/import documents
        ↓
Discuss the project with AI
        ↓
AI searches and understands relevant documents
        ↓
AI identifies affected documents
        ↓
AI proposes changes
        ↓
User reviews changes
        ↓
User accepts or rejects changes
        ↓
Documents are updated together
```

Users should remain in control of document modifications.

AI should propose meaningful changes and explain why they are needed rather
than silently rewriting a project.

---

## Documents as Living Knowledge

MarkdownGPT should treat documents as living representations of a project,
not static files.

As a project evolves, documents should evolve with it.

The system should help identify:

- Outdated assumptions
- Contradictory statements
- Duplicate information
- Missing documentation
- Terminology inconsistencies
- Decisions that affect multiple documents

Eventually, MarkdownGPT should be capable of answering questions such as:

> Which documents are affected by this decision?

> Does anything in this project contradict our new architecture?

> Where did we originally decide to use this approach?

> What changed in the project over the last month?

> Are our product requirements consistent with our technical architecture?

> Which assumptions haven't been revisited recently?

---

## Project Decisions

Important decisions should be distinguishable from ordinary conversation.

For example:

```text
Decision

Do not depend on unofficial provider APIs.

Status
Accepted

Rationale
Unofficial APIs create reliability and platform-risk concerns.

Implications
- Use alternative data sources.
- Preserve provider abstractions.
- Pursue official partnerships where appropriate.
```

Decisions provide durable context that can influence future AI suggestions.

This allows MarkdownGPT to understand not only **what the documents currently
say**, but also **why the project arrived there**.

---

## Markdown as the Foundation

Markdown is the underlying document format because it is:

- Simple
- Portable
- Human-readable
- Machine-readable
- Version-friendly
- Widely supported
- Well suited for AI processing

However, users should not need to understand Markdown to use MarkdownGPT.

The primary experience should feel like a modern document workspace.

Markdown is the underlying representation, not a prerequisite for using the
product.

---

## Portability

A core principle of MarkdownGPT is:

**Your documents belong to you.**

Users should never be trapped inside a proprietary document format.

Documents should eventually be exportable as formats such as:

- Markdown
- PDF
- DOCX
- Project archives

Integrations may also allow documents to synchronize with external systems
such as source-control or document platforms.

GitHub should be an optional integration rather than a requirement for using
MarkdownGPT.

---

## Who MarkdownGPT Is For

MarkdownGPT should not be limited to software developers.

Potential users include:

- Founders
- Product managers
- Engineers
- Researchers
- Students
- Writers
- Consultants
- Small businesses
- Project teams
- Anyone maintaining a collection of related documents

The common characteristic is not technical expertise.

It is having **multiple documents that describe the same evolving body of
work**.

---

## AI-Native Search

Search is not only a user-facing feature.

Search is part of how MarkdownGPT understands a project.

When a user introduces a new decision, the system should be capable of
finding semantically related information across the project's documents,
even when those documents use different terminology.

For example:

```text
User:
"We aren't going to rely on provider APIs anymore."

Relevant information discovered:

technical-architecture.md
  "Pricing is retrieved through provider integrations..."

product-requirements.md
  "The system shall retrieve live provider pricing..."

roadmap.md
  "Phase 2: Integrate provider pricing APIs..."
```

This allows the AI to reason across the project instead of relying only on
the document currently open.

---

## Trust and User Control

MarkdownGPT should make AI changes understandable and reversible.

Users should be able to see:

- What the AI wants to change
- Which documents will change
- Why each change is necessary
- The previous content
- The proposed content

Users should be able to accept or reject changes before they become part of
the project.

Document history should allow previous versions to be recovered.

---

## What MarkdownGPT Is Not

MarkdownGPT is not primarily:

- A Markdown syntax editor
- A generic chatbot
- A GitHub client
- A replacement for source control
- A simple AI text generator
- A file-storage service with an AI button

Those capabilities may exist within the product, but they are not the core
value proposition.

The core value is **understanding and maintaining a connected body of
documentation**.

---

## Initial Product

The first version should focus on proving the central workflow.

Users should be able to:

1. Create a project.
2. Create Markdown documents.
3. Edit and preview documents.
4. Import existing Markdown documents.
5. Ask questions about the project.
6. Search across project documents.
7. Ask AI to modify a document.
8. Have AI identify other documents affected by a change.
9. Review proposed modifications.
10. Accept or reject those modifications.
11. View previous versions of documents.
12. Download their Markdown files.

Features outside this workflow should be considered secondary until the
core experience is proven.

---

## Future Direction

Over time, MarkdownGPT can evolve from an AI document editor into a
**project knowledge and documentation intelligence system**.

The system could understand:

```text
Documents
    +
Conversations
    +
Decisions
    +
History
    +
Relationships
    ↓
Project Knowledge
```

This would allow MarkdownGPT to do more than generate text.

It could help users understand how their thinking evolved, identify when
their documentation no longer reflects reality, surface conflicts between
documents, and maintain consistency as projects become increasingly complex.

---

## Product Principle

A project should not become harder to document as it becomes more complex.

MarkdownGPT should make the opposite true:

**The more context MarkdownGPT understands about a project, the more useful
it becomes at keeping that project coherent.**
