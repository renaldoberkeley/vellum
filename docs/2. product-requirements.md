# Vellum - Product Requirements

> Internal codename for MarkdownGPT.

## 1. Purpose

This document defines the product requirements for the initial version of
MarkdownGPT.

MarkdownGPT is an AI-native workspace for creating, organizing, searching,
and maintaining collections of related documents.

The core product promise is:

**Tell MarkdownGPT what changed. MarkdownGPT determines what documentation
needs to change with it.**

---

## 2. Product Goals

MarkdownGPT should allow users to:

1. Organize related documents into projects.
2. Create and edit documents through a modern document editor.
3. Use AI to create and modify documents.
4. Ask questions across all documents in a project.
5. Search project documents using both traditional and semantic search.
6. Identify documents affected by a new decision or change.
7. Propose coordinated modifications across multiple documents.
8. Review AI-generated changes before applying them.
9. Maintain document version history.
10. Import and export documents without being locked into MarkdownGPT.

---

## 3. Non-Goals for Initial Release

The initial version will not attempt to provide:

- Real-time collaborative editing
- Enterprise document management
- Complex workflow automation
- Git-based version control
- Native GitHub synchronization
- Mobile applications
- Offline editing
- Full Microsoft Word feature compatibility
- Large-scale organizational knowledge management

These capabilities may be considered after the core workflow has been
validated.

---

## 4. Core Concepts

### 4.1 Workspace

A workspace represents the top-level environment owned by a user or,
eventually, a team.

For the initial version, each user may have a personal workspace.

### 4.2 Project

A project contains a related collection of documents and associated AI
context.

Example:

```text
Rideboard
├── Vision
├── Product Requirements
├── Technical Architecture
├── Engineering Principles
└── Fare Intelligence
```

AI interactions should generally operate within the context of a project.

### 4.3 Document

A document is a piece of content belonging to a project.

Markdown is the canonical underlying representation.

A document contains at minimum:

- Title
- Markdown content
- Project
- Creation timestamp
- Last modification timestamp
- Version information

### 4.4 Document Version

Every accepted modification should create a recoverable version.

Users should be able to inspect previous versions and understand what
changed.

### 4.5 Conversation

Users can have AI conversations associated with a project.

The AI should be capable of retrieving relevant project documents when
responding.

### 4.6 Decision

A decision represents an important conclusion that should persist beyond
an individual AI conversation.

A decision may contain:

- Title
- Description
- Status
- Rationale
- Date
- Related documents
- Implications

Decisions may be used as durable context for future AI interactions.

## 5. Project Management Requirements

### PR-PROJ-001 - Create Project

Users shall be able to create a project.

A project shall include:

- Name
- Optional description
- Creation timestamp
- Last updated timestamp

### PR-PROJ-002 - View Projects

Users shall be able to view their projects from a project dashboard.

### PR-PROJ-003 - Rename Project

Users shall be able to rename an existing project.

### PR-PROJ-004 - Delete Project

Users shall be able to delete a project.

Deletion should require explicit confirmation.

---

## 6. Document Requirements

### PR-DOC-001 - Create Document

Users shall be able to create a document inside a project.

### PR-DOC-002 - Edit Document

Users shall be able to edit document content.

The editor should provide a modern writing experience without requiring
users to understand Markdown syntax.

### PR-DOC-003 - Markdown Representation

Documents shall have Markdown as their canonical portable representation.

### PR-DOC-004 - Rendered View

MarkdownGPT shall render Markdown content as formatted documents.

### PR-DOC-005 - Rename Document

Users shall be able to rename documents.

### PR-DOC-006 - Delete Document

Users shall be able to delete documents.

### PR-DOC-007 - Document Navigation

Users shall be able to easily navigate between documents within a project.

---

## 7. Import and Export

### PR-IO-001 - Import Markdown

Users shall be able to upload existing `.md` files into a project.

### PR-IO-002 - Export Markdown

Users shall be able to download an individual document as a `.md` file.

### PR-IO-003 - Export Project

Users should eventually be able to export all project documents together.

The initial implementation may use a ZIP archive containing Markdown files.

### PR-IO-004 - Future Formats

The architecture should allow future support for:

- PDF
- DOCX
- TXT
- Additional document formats

---

## 8. Search Requirements

### PR-SEARCH-001 - Project Search

Users shall be able to search across all documents within a project.

### PR-SEARCH-002 - Keyword Search

Search shall support exact and lexical text matching.

Example:

> Find every mention of "Uber API".

### PR-SEARCH-003 - Semantic Search

Search should support queries based on meaning rather than exact wording.

Example:

> Where did we discuss alternatives to third-party pricing providers?

Relevant results may be returned even when those exact words do not appear
in the documents.

### PR-SEARCH-004 - Search Results

Search results should identify:

- Document
- Relevant section
- Matching content
- Relevance

### PR-SEARCH-005 - AI Retrieval

The AI shall be able to use document search automatically when additional
project context is required.

Search is therefore both a user-facing capability and an internal AI
capability.

---

## 9. AI Conversation Requirements

### PR-AI-001 - Project Chat

Users shall be able to have an AI conversation associated with a project.

### PR-AI-002 - Project Context

The AI shall be capable of retrieving relevant information from documents
within the current project.

### PR-AI-003 - Document Questions

Users shall be able to ask questions about individual documents.

### PR-AI-004 - Cross-Document Questions

Users shall be able to ask questions requiring information from multiple
documents.

Example:

> Does our technical architecture satisfy the requirements in the product
> requirements document?

### PR-AI-005 - Source Awareness

When practical, AI responses should indicate which project documents or
sections were used to formulate an answer.

---

## 10. AI Document Generation

### PR-GEN-001 - Generate Document

Users shall be able to ask AI to generate a new document.

Example:

> Create a technical architecture document based on the product requirements.

### PR-GEN-002 - Project-Aware Generation

Generated documents should incorporate relevant information already present
in the project.

### PR-GEN-003 - Generate Sections

Users shall be able to ask AI to create individual sections within an
existing document.

---

## 11. AI Document Modification

### PR-EDIT-001 - Request Modification

Users shall be able to describe a desired project or document change using
natural language.

Example:

> We decided not to depend on third-party pricing APIs.

### PR-EDIT-002 - Impact Analysis

MarkdownGPT should search the project to determine which documents may be
affected by the requested change.

### PR-EDIT-003 - Proposed Changes

MarkdownGPT shall present proposed modifications before applying them.

### PR-EDIT-004 - Change Explanation

Each proposed modification should include an explanation of why the document
is affected.

### PR-EDIT-005 - Multi-Document Changes

A single user request may generate proposed changes to multiple documents.

### PR-EDIT-006 - Selective Approval

Users should be able to accept or reject individual proposed changes.

### PR-EDIT-007 - No Silent Modification

AI-generated modifications shall not alter documents without user approval.

---

## 12. Change Review

The change-review experience is a core part of MarkdownGPT.

Users should see something conceptually similar to:

```text
3 documents affected

Product Requirements
────────────────────
1 proposed change

Technical Architecture
──────────────────────
3 proposed changes

Roadmap
───────
1 proposed change

                Review Changes
```

When reviewing a specific modification, users should be able to compare:

```diff
- Pricing is retrieved directly from provider APIs.

+ Pricing may be obtained from community observations,
+ approved integrations, and internal estimation models.
```

The user may then:

- Accept
- Reject
- Request revision

---

## 13. Version History

### PR-VER-001 - Automatic Version Creation

Accepted AI modifications shall create a new document version.

Significant manual modifications should also be versioned.

### PR-VER-002 - Version History

Users shall be able to view previous versions of a document.

### PR-VER-003 - Change Metadata

Versions should contain:

- Timestamp
- Change source
- Optional summary
- Previous version relationship

### PR-VER-004 - Restore Version

Users should be able to restore a previous document version.

Restoring an older version should itself create a new version rather than
destroying history.

---

## 14. Project Decisions

### PR-DEC-001 - Create Decision

Users shall be able to save important project decisions.

### PR-DEC-002 - AI Suggested Decisions

The AI may suggest converting an important conclusion from a conversation
into a project decision.

The user must approve creation of the decision.

### PR-DEC-003 - Decision Context

Relevant accepted decisions should be available to AI interactions within
the project.

### PR-DEC-004 - Decision Status

Decisions should support statuses such as:

- Proposed
- Accepted
- Superseded

### PR-DEC-005 - Decision Relationships

A decision may reference documents or other decisions affected by it.

---

## 15. Consistency Intelligence

### PR-CONSIST-001 - Contradiction Detection

MarkdownGPT should be capable of identifying potentially contradictory
statements across project documents.

### PR-CONSIST-002 - Outdated Information

MarkdownGPT should eventually identify information that may have become
outdated because of newer accepted decisions.

### PR-CONSIST-003 - Terminology Consistency

MarkdownGPT should help identify inconsistent terminology across documents.

### PR-CONSIST-004 - Missing Updates

When a document changes substantially, MarkdownGPT should be capable of
identifying other documents that may also require updates.

---

## 16. AI Transparency

MarkdownGPT should make it clear when content was:

- Written manually
- Generated by AI
- Modified by AI
- Restored from history

Users should be able to understand why the AI recommends a change.

AI confidence should not be presented as certainty when relationships
between documents are ambiguous.

---

## 17. Portability

Users retain ownership of their documents.

MarkdownGPT shall not require a proprietary format to access project
content.

At minimum, users shall be able to export documents as Markdown.

The system should be designed so that additional integrations can be added
later without making an external platform the required source of truth.

---

## 18. Initial User Experience

A new user should be able to move through the following workflow:

```text
Sign up
   ↓
Create Project
   ↓
Create document / Import Markdown
   ↓
Write or generate content
   ↓
Create additional related documents
   ↓
Ask AI questions about the project
   ↓
Tell AI something changed
   ↓
AI identifies affected documents
   ↓
Review proposed changes
   ↓
Accept selected changes
   ↓
New document versions created
```

This workflow represents the primary experience that the initial product
must prove.

## 20. Success Criteria

The initial product should demonstrate that a user can maintain a project
containing multiple related documents with less manual coordination than
using independent document editors or isolated AI conversations.

The defining test is:

> Can a user describe an important project change once and have MarkdownGPT
> correctly identify and propose updates to the relevant documents?

If MarkdownGPT can reliably accomplish that while keeping the user in
control of the changes, the core product hypothesis is validated.
