
# Vellum — Technical Architecture

> Internal codename for MarkdownGPT.

## 1. Purpose

This document describes the technical architecture for MarkdownGPT.

The architecture is designed around three principles:

1. Build the smallest architecture necessary to support the initial product.
2. Preserve clear boundaries that allow more sophisticated AI and search
   capabilities to be introduced later.
3. Avoid infrastructure complexity until product requirements justify it.

The initial architecture should support Milestone 1 while providing a clear
evolution path toward Milestones 2 and 3.

---

## 2. Product Architecture Roadmap

MarkdownGPT will evolve through three primary technical milestones.

### Milestone 1 — AI Project Workspace

Users can:

- Create projects
- Create and edit Markdown documents
- Import existing Markdown documents
- Ask AI questions about a project
- Generate documents using project context
- Maintain basic document version history

For small projects, relevant project documents may be supplied directly to
the LLM without requiring a dedicated retrieval system.

### Milestone 2 — Project Change Intelligence

MarkdownGPT introduces:

- Document impact analysis
- Coordinated multi-document modifications
- Proposed-change review
- Diff generation
- Selective change approval
- More sophisticated document retrieval

### Milestone 3 — Project Knowledge Intelligence

MarkdownGPT introduces:

- Semantic search
- Embeddings
- Project decisions
- Contradiction detection
- Outdated-information detection
- Terminology consistency analysis
- Project knowledge relationships

## 4. Frontend

### Technology

The web application will use:

**Next.js + TypeScript**

The frontend is responsible for:

- Authentication experience
- Project dashboard
- Document navigation
- Document editing
- Markdown rendering
- AI conversation interface
- Proposed-change review
- Version-history UI

### Primary Workspace

The core interface should use a three-panel layout:

```text
┌──────────────┬──────────────────────────┬─────────────────────┐
│ Documents    │ Document                 │ AI                  │
│              │                          │                     │
│ vision.md    │ # Product Vision         │ Ask about this      │
│ requirements │                          │ project...          │
│ architecture │ Markdown content...      │                     │
│              │                          │                     │
│ + Document   │                          │                     │
└──────────────┴──────────────────────────┴─────────────────────┘
```

The interface should remain usable when the AI panel is collapsed.

---

## 5. Backend

### Technology

The application backend will use:

**Python + FastAPI**

FastAPI is responsible for:

- Application APIs
- Authentication authorization enforcement
- Project operations
- Document operations
- Version management
- Search/retrieval
- AI orchestration
- Import/export operations

The backend should contain application logic rather than placing significant
business logic in the frontend.

---

## 6. Primary Database

### Technology

**PostgreSQL**

PostgreSQL will be the primary system of record.

It will store:

- Users
- Workspaces
- Projects
- Documents
- Markdown content
- Document versions
- Conversations
- Messages
- Project decisions
- AI change proposals
- Metadata

Markdown content will initially be stored directly in PostgreSQL using text
columns.

PostgreSQL is preferred because MarkdownGPT's domain contains strongly
related entities and requires transactional operations, version history,
permissions, and structured querying.

## 8. Document Storage

Markdown documents will initially be stored directly in PostgreSQL.

For example:

```text
documents.markdown_content TEXT
```

This provides:

- Simple transactional updates
- Straightforward version creation
- Easy querying
- Simple backups
- No separate document-storage system

MarkdownGPT should not require Git or GitHub for document storage.

GitHub may later become an optional integration.

---

## 9. Object Storage

Object storage is not required for the earliest Milestone 1 implementation.

When binary content becomes necessary, S3-compatible object storage should
be introduced.

Potential uses include:

- Images
- PDF uploads
- DOCX uploads
- Attachments
- Generated PDFs
- Generated DOCX files
- ZIP project exports

PostgreSQL should store metadata and references to these objects rather than
large binary files themselves.

---

## 10. Document Versioning

MarkdownGPT will maintain application-level document version history.

When a document update requiring versioning occurs:

```text
Current Document
       │
       ▼
Create DocumentVersion
       │
       ▼
Update Document
       │
       ▼
Commit Transaction
```

Both operations should occur within the same database transaction.

Restoring an old version should create a new version rather than deleting
subsequent history.

---

## 11. AI Architecture

AI functionality should be accessed through an internal abstraction rather
than directly throughout application code.

Conceptually:

```python
class LLMProvider:
    async def generate(self, request):
        ...
```

Implementations may include:

```text
OpenAIProvider
FutureProvider
```

The rest of the application should interact with the abstraction rather
than provider-specific SDK calls wherever practical.

This allows models and providers to evolve without requiring major changes
to document or project logic.

---

## 12. Project Context — Milestone 1

Milestone 1 should prioritize simplicity.

For sufficiently small projects, MarkdownGPT may construct project context
directly from the project's documents.

Conceptually:

```text
System Instructions

Project Context

--- vision.md ---
<content>

--- product-requirements.md ---
<content>

--- technical-architecture.md ---
<content>

Conversation Context

User Request
```

This avoids introducing embeddings and vector retrieval before they are
necessary.

The context builder must enforce model context limits.

When project content becomes too large, the retrieval architecture described
later in this document should be used.

---

## 13. Context Builder

AI requests should pass through a dedicated context-building service.

```text
User Request
     │
     ▼
ContextBuilder
     │
     ├── Current Document
     ├── Relevant Project Documents
     ├── Relevant Decisions
     └── Conversation History
     │
     ▼
LLM Provider
```

For Milestone 1, `Relevant Project Documents` may mean all project
documents when the project is sufficiently small.

This abstraction prevents AI request construction from becoming scattered
throughout the backend.

---

## 14. Search Architecture

Search should be treated as its own application capability.

Define a logical interface such as:

```python
class SearchService:
    async def search(
        self,
        project_id,
        query,
        filters=None,
    ):
        ...
```

The initial implementation may use PostgreSQL text-search capabilities.

The rest of the application should not depend directly on the underlying
search implementation.

This allows:

```text
PostgresSearchBackend
          ↓
Future
          ↓
HybridSearchBackend
          ↓
Possible dedicated search infrastructure
```

without changing higher-level AI workflows.

---

## 15. Semantic Search

Semantic search is not required to complete the earliest Milestone 1.

When needed, MarkdownGPT can introduce document chunking and vector
embeddings.

A possible future model is:

```text
Document
   │
   ▼
DocumentChunk
   ├── content
   ├── document_id
   ├── section
   ├── position
   └── embedding
```

PostgreSQL with `pgvector` is the preferred initial vector-search approach.

This avoids introducing a separate vector database prematurely.

---

## 16. Future Hybrid Retrieval

As search requirements grow, MarkdownGPT should support hybrid retrieval:

```text
                    User Query
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
        Lexical Search      Vector Search
              │                   │
              └─────────┬─────────┘
                        ▼
                  Merge / Rerank
                        │
                        ▼
                 Relevant Chunks
                        │
                        ▼
                       LLM
```

This provides both:

- Exact terminology matching
- Meaning-based retrieval

A dedicated search engine such as OpenSearch or Elasticsearch may eventually
be introduced if scale or search requirements justify it.

It is not required for the initial architecture.

Proposed AI modifications should be stored separately from canonical
documents until accepted.

Conceptually:

```text

```

Possible statuses:

```text

rejected

```

This prevents AI-generated content from silently becoming canonical project
documentation.

The backend API should be organized around product domains rather than
individual UI screens.

For example:

```text

/api/documents/{id}/versions
/api/conversations
/api/search
/api/ai/chat
/api/ai/generate
/api/changes
/api/decisions
```

Exact endpoint definitions should be established during implementation.

---

## 22. Authentication

Authentication should be implemented using a proven authentication solution
rather than building password and identity infrastructure from scratch.

The application backend remains responsible for authorization.

Every project/document operation must verify that the authenticated user has
permission to access the associated workspace/project.

The architecture should allow team membership and more sophisticated
permissions to be introduced later.

---

## 23. Background Processing

A background task system should not be introduced until workloads require it.

Milestone 1 AI requests may initially execute through normal application
request flows or streaming responses.

Background workers may later handle:

- Document indexing
- Embedding generation
- Large imports
- Project analysis
- Export generation
- Consistency scans

Redis or another queue infrastructure should only be introduced when these
requirements become concrete.

---

## 24. Streaming

AI responses should support streaming to provide immediate feedback during
generation.

Conceptually:

```text
Browser
   │
   │ request
   ▼
FastAPI
   │
   ▼
LLM
   │
   │ streamed tokens/events
   ▼
FastAPI
   │
   ▼

```

The exact transport may be selected during implementation.

---

## 25. Security Principles

The application should follow several baseline principles:

- Users may access only authorized projects and documents.
- Project authorization must be enforced server-side.
- Secrets must never be stored in source control.
- LLM API credentials remain server-side.
- Uploaded files should be treated as untrusted input.
- AI-generated modifications require explicit approval before becoming
  canonical documents.
- External integrations should use scoped credentials where possible.

---

## 26. Observability

The application should eventually capture:

- API errors
- AI provider errors
- AI latency
- Token usage
- Search latency
- Document modification failures
- Import/export failures

The initial implementation should prioritize structured application logging
without requiring a large observability stack.

## 29. Architecture Principles

### Keep the Source of Truth Simple

PostgreSQL is the canonical source of truth for application and Markdown
document data.

Search indexes, embeddings, caches, and external integrations are derived
systems and should be rebuildable.

### AI Does Not Own Canonical Content

AI proposes.

Users approve.

Only approved content becomes part of canonical documents.

### Search Is an Abstraction

Application logic should depend on `SearchService`, not directly on
PostgreSQL, pgvector, Elasticsearch, or another search technology.

### LLM Providers Are Replaceable

Core application logic should not depend unnecessarily on one model or
provider.

### Add Infrastructure When Required

Do not introduce Redis, Elasticsearch, Kubernetes, vector databases, or
complex distributed systems merely because they may eventually be useful.

### Portability Matters

Markdown remains the canonical portable representation of document content.

### Build for Dogfooding

The first meaningful technical milestone is reached when MarkdownGPT can be
used to help maintain MarkdownGPT's own documentation.

---

## 30. Initial Technical Success Criterion

Milestone 1 is technically successful when the Vellum project itself can be
imported into MarkdownGPT and a user can ask:

> Based on vision.md and product-requirements.md, help me update
> technical-architecture.md.

MarkdownGPT should understand the relevant project context, generate a useful
proposal, allow the user to review it, and persist the accepted document
change with version history.

At that point, MarkdownGPT becomes capable of participating in its own
development.
